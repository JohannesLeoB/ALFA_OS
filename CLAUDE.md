Only such a ZIP is a valid master and reference; it is stored in the repository as the latest and the previous master, and the newest hands over to the next.

- Work style: read every file before changing it; no blanket cuts or search-and-replace edits; ask before removing anything not proven dead. Old quotes in archived notes are not binding.
- Mail and Hub were rewritten without legacy code; integrations were adopted file by file.
- The Claude assistant (37 tools) and the calculation it drives are kept; calculation numbers and model routing stay unchanged.
- Finished but unwired parts stay `internal` and are not deleted: 9 assistant tools, DHL labels (`LabelClient`, `LabelState`), the Clockodo time table (`TimeTableState`, `BookingEngine`). The calculation learning stores (`LearningStore`, `LearnedAnchorStore`, `PdfAnchorStore`) are wired in `ToolShelf` (in `App/Shell/Assembly.swift`).
- Team and roles (Johannes 31.10.): roles never depend on a service such as Airtable or Clockodo, because not every company has one. The team list is an ALFA file (`ALFA Team/team.json`) in any shared folder (Drive, iCloud, Dropbox, network share), held through a security-scoped bookmark. Two roles, Admin and Team; alone means Admin and everything free; only "Team teilen" creates the file, only Admins write, the last Admin stays; identity comes only from a Google or Microsoft sign-in, never from an IMAP login. No Touch ID, no model cap (the routing stays unchanged), no automatic deletion of conversations. A broken file keeps the last valid stand instead of opening everything. The rule applies as AND of company, role and the person's own switches.
- Assistant (Johannes 31.10.): area A (full area with lanes for conversations, chat and context) and the blob panel B share one conversation; every action with outward effect is proposed first and confirmed in the chat; company and price knowledge needs a source with a quote and an Admin's approval before it counts, and it never feeds the calculation. The knowledge and file tools stay `internal` until Design delivers area A.
- Name (Johannes 31.10.): the app is called "ALFA_OS" in every user-visible text; bundle id, Application Support folder and keychain names stay. The Google consent screen shows the app name of the Google Cloud project (809584755103), which Johannes changes in the Cloud Console.

- Mail range (Johannes 29.10.): each mailbox loads a time range, set in its settings card under "Laden": 30 days (default), 90 days, 1 year or all. Every choice is offered only when the transport can do it (`MirrorPort`, `EverywhereSearchPort`). Known limit: Gmail list rows come from `format=metadata`, so their attachment count is a guess (1 for any `multipart/mixed`, no names) until the message is opened. Open: a size limit in MB and storing attachments locally.
- Mail is a client (Johannes 29.10.): ALFA_OS Mail is a mail program like macOS Mail, never the service. Everything on the server belongs to the provider; ALFA mirrors, shows and sends. Removing an account deletes only the local copy. The behaviour standard is what established mail programs do (a function counts as standard when at least two of macOS Mail, Outlook, Thunderbird and the Gmail client have it); the look follows the bow; what the standard has and the bow lacks becomes an order to Design. "Blind bedienbar" is meant as self-evident use, not keyboard-only; SPEC.md keeps operation by mouse.
- Accounts (Johannes 29.10.): Mail, Settings and accounts are one interlocking system, built universally for any number of accounts (the limit of 3 falls), two Gmail accounts, Gmail plus IMAP; which Google services a second Google account brings is decided after checking the Google documentation.
